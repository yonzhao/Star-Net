## 架构概览

名称取自图面，下列职责只是图示概括，不代表已实现功能。

- **三方系统**：位于架构图底部，与主控为“接口交互”（双向箭头），可视为外部调用方。
- **主控模块**：架构图中连接三方、动捕与渲染，时序图中创建并访问共享内存，图中承担协调角色。
- **动捕模块**：包含目标检测、头部姿态推理、人脸表情推理、身体推理、手部推理和后处理。
- **渲染模块**：图中未列出内部组件；“负责渲染”是据名称的概括。
- **共享内存**：时序图中的独立生命线，图中出现创建、读写和重置相关消息。

动捕内部：目标检测是入口，分别指向头部姿态、身体和手部推理；头部姿态再指向人脸表情；身体、手部及由头部姿态引出的表情最终汇入后处理。图中未画表情与身体/手部推理的关系。

模块关系：

- 主控指向动捕的单箭头旁标“控制流”；该边两端均未绑定 source/target，按几何位置判断。
- 主控与渲染之间有两条边：单向边旁标“控制流”；另一条双向边没有独立说明，其语义待确认。
- 主控与动捕、渲染与动捕之间的双向边旁标“数据流”；这些边两端均未绑定 source/target，按几何位置判断。
- 三方与主控之间为双向箭头，标注“接口交互”。

图纸未画三方与动捕/渲染的直接连接，也未说明共享内存布局、同步方式和访问协议。缺少端点锚定只表示绘图时未绑定，不代表连线缺失。

图纸底部只有 `input(128x128)`、`CONV(16x3x7x7)`、`CONV(NxCxWxH)`、`relu` 以及 **CONV BLOCK1**、**CONV BLOCK2** 等标签，未画出任何连线。其排列顺序、是否构成网络层次、对应哪个模型或哪一路推理均待确认；N、C、W、H 的图注分别为卷积核个数、通道数、宽、高。

## 生命周期概览

时序图有五条生命线：三方、主控、动捕、渲染和共享内存。按图面顺序归纳：

1. **创建**：三方先“初始化”，再调用“创建数字人服务”；主控创建共享内存、启动 socket 服务并返回。
2. **启动**：三方调用“启动数字人服务”；主控分别向动捕和渲染发送“启动命令”；动捕“绑定共享内存”，渲染“加载模型”并“绑定共享内存”。
3. **运行**：三方发起“服务执行”；主控执行“参数校验/格式转换”，并有“数据写入共享内存”；动捕读取数据并执行“动捕处理”；渲染执行“渲染”；主控读取共享内存后以“callback”回调三方。
4. **停止**：三方调用“停止服务”；主控执行“共享内存重置”，并分别向动捕和渲染发送“停止”。
5. **销毁**：三方调用“销毁服务”，主控随后向动捕和渲染发送“销毁”。

以上仅为图面表达，不构成协议：图中没有消息格式、错误码、超时、重试、线程模型或时序保证。部分消息边未绑定端点：“读数据”“写数据”只有 target（共享内存），缺 source；“数据写入共享内存”两端均未绑定；发往渲染的“销毁”只有 target（渲染），缺 source。相关发起方按几何位置推断，需结合实现确认。socket 服务只见于主控自身消息，端口、协议和通信对端均未说明。

## 待确认问题

以下均为**设计待确认项**，不是已在代码中证实的缺陷：

1. 三方与主控的接口契约是什么（请求/响应字段、同步或异步、callback 的触发条件和返回值）？
2. 主控启动的 socket 服务与动捕、渲染是什么关系？“启动命令”“停止”“销毁”是否也通过 socket 下发？
3. 共享内存的数据布局、读写同步、并发保护和生命周期管理如何定义？图中仅有读写与重置动作。
4. 各模块（主控、动捕、渲染）分别读写共享内存的哪些区域？数据布局与同步策略如何定义，如何避免覆盖或半更新数据？
5. 停止和销毁阶段，动捕、渲染、模型与共享内存的资源回收顺序及失败补偿是什么？
6. 动捕的头部姿态、表情、身体、手部推理是否共用同一份目标检测结果？表情推理是否依赖身体或手部信息？
7. 底部的 CONV BLOCK1/CONV BLOCK2 等标签对应哪个模型、哪一路推理？它们之间缺少连线是省略还是另有含义？
8. 主控与渲染之间的双向边与单向边分别代表什么？双向边是否也属于控制流？
