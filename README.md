## 架构概览

图中参与方与角色：

- **三方系统**：外部调用方，与主控模块之间为“接口交互”（双向箭头）。
- **主控模块**：协调者，负责与三方系统交互，并连接动捕、渲染和共享内存。
- **动捕模块**：包含目标检测、头部姿态推理、人脸表情推理、身体推理、手部推理和后处理。
- **渲染模块**：负责数字人渲染。
- **共享内存**：时序图中的独立生命线，作为模块间数据交换的载体。

动捕模块内部：目标检测是入口，分别指向头部姿态推理、身体推理和手部推理；头部姿态推理再指向人脸表情推理；身体、手部及由头部姿态引出的人脸表情最终汇入后处理。图中没有画出表情推理与身体/手部推理的关系。

模块之间的关系：

- 控制流：主控模块指向动捕模块（向上单箭头，未锚定端点，按几何位置判断）；主控模块与渲染模块之间同时存在单箭头和双向箭头，该组连线标注“控制流”。
- 数据流：主控模块与动捕模块、渲染模块与动捕模块之间均为双向箭头（未锚定端点，按几何位置判断）。
- 接口交互：三方系统与主控模块之间为双向箭头。

图纸没有画出三方系统与动捕/渲染的直接连接，也没有说明共享内存的具体布局、同步方式和访问协议。缺少端点锚定仅表示绘图时未绑定，不代表连线缺失。

图纸底部另有 **CONV BLOCK1**（自上而下为 `input(128x128)`、`CONV(16x3x7x7)`、`CONV(NxCxWxH)`、`relu`）和 **CONV BLOCK2**（`CONV(NxCxWxH)`、`relu`），并注明 N、C、W、H 分别为卷积核个数、通道数、宽、高。块内方框之间及两个块之间均未画出连线，也未与动捕模块中的任何一路推理建立对应关系，只能视为网络结构的片段示意。

## 生命周期概览

时序图有五条生命线：三方系统、主控、动捕、渲染和共享内存。按图面顺序归纳为：

1. **创建**：三方系统调用“创建数字人服务”；主控模块创建共享内存并启动 socket 服务，随后向动捕模块和渲染模块分别发送“启动命令”。
2. **启动**：动捕模块“绑定共享内存”；渲染模块“加载模型”并“绑定共享内存”。
3. **运行**：三方系统发起“服务执行”；主控模块执行“参数校验/格式转换”，并有“数据写入共享内存”；动捕模块读取数据并执行“动捕处理”；渲染模块执行“渲染”；主控模块读取共享内存后以“callback”回调三方系统。
4. **停止**：三方系统调用“停止服务”；主控模块执行“共享内存重置”，并分别向动捕模块和渲染模块发送“停止”。
5. **销毁**：三方系统调用“销毁服务”，主控模块随后向动捕模块和渲染模块发送“销毁”。

以上仅为图面表达，不构成协议：图中没有消息格式、错误码、超时、重试、线程/进程模型或时序保证。标注“读数据”“数据写入共享内存”的连线未绑定端点，按几何位置推断为动捕读取、主控写入，需结合实现确认。socket 服务只见于主控自身消息，端口、协议和通信对端均未说明。

## 待确认问题

以下均为**设计待确认项**，不是已在代码中证实的缺陷：

1. 三方系统与主控模块的接口契约是什么（请求/响应字段、同步或异步、callback 的触发条件和返回值）？
2. 主控模块启动的 socket 服务与动捕、渲染模块之间是什么关系？“启动命令”“停止”“销毁”是否也通过 socket 下发？
3. 共享内存的数据布局、读写同步、并发保护和生命周期管理如何定义？图中仅有读写与重置动作。
4. 动捕写入、渲染读取与主控读取的先后顺序如何保证？是否可能覆盖或读到半更新数据？
5. 停止和销毁阶段，动捕模块、渲染模块、模型与共享内存的资源回收顺序及失败补偿是什么？
6. 动捕内部的头部姿态、表情、身体、手部推理是否共用同一份目标检测结果？表情推理是否依赖身体或手部信息？
7. 底部的 CONV BLOCK1/CONV BLOCK2 对应哪个模型、哪一路推理？两个块之间缺少连线是省略还是另有含义？
8. 主控与渲染之间同时出现单箭头和双向箭头，分别代表调用、通知还是其他语义？
